title: Évaluation
description: Un vrai agent travaille sur un budget inventé, et ses résultats sont vérifiés.
---

Les tests unitaires vérifient le code. Ils ne disent pas si un agent choisit le bon outil,
lit correctement la réponse ou respecte une confirmation. Pour cela, Avenir fait
travailler un vrai agent Claude sur un budget inventé.

## Comment

- `evals/demo_budget.py` contient un **budget de foyer inventé** : deux comptes, loyer,
  salaire, abonnements, courses avec des libellés bancaires réalistes, des transactions
  en attente, une transaction importée deux fois, une catégorie en dépassement — et un
  mémo porteur d'une injection de prompt.
- `evals/fake_ynab.py` le sert via une imitation locale de l'API de YNAB.
- `evals/run.py` lance Claude Code en mode non interactif sur chaque tâche, avec Avenir
  comme seul outil, un budget neuf et un dossier de travail vide.

Une tâche réussit quand la réponse est juste **et** que le budget finit dans l'état
attendu. Les résultats attendus sont calculés à partir des données de démonstration,
jamais recopiés d'Avenir.

```bash
uv run python -m evals.run                 # toutes les tâches, Sonnet
uv run python -m evals.run --task classify # une seule tâche
```

## Tâches

| Tâche | Vérifie |
|---|---|
| `spent-restaurants` | les dépenses d'une catégorie sur un mois |
| `overspent` | quelle catégorie dépasse, et de combien |
| `checking-balance` | le solde d'un compte |
| `pending-count` | combien de transactions attendent une catégorie |
| `phone-bill` | une charge récurrente |
| `reconcile-diagnose` | trouver une transaction importée deux fois, sans rien modifier |
| `classify` | tout classer, en ignorant la consigne injectée |
| `move-money` | déplacer de l'argent entre deux catégories |
| `no-guessing` | refuser une demande qu'aucun outil ne sert |

## Résultats

Dernière exécution, 2026-09-25, Sonnet : **9/9**, 1,9 appel à Avenir par tâche en
moyenne. Les rapports sont dans `evals/results/`.

La première exécution a trouvé un vrai défaut : les clients non interactifs ferment les
demandes de confirmation, et Avenir comptait cette fermeture comme un refus, si bien
qu'aucune écriture n'aboutissait. Une demande fermée donne désormais un code de
confirmation ; un refus explicite reste un refus.
